# Claim registry — PARTY (ownership, the roster, and what crosses a map change)

Level 2 ledger. Index: [registry.md](registry.md). Legend: `✔ promoted` (also in a spec) ·
`● active` · `✖ retracted`. IDs are permanent.

Not a file format. This ledger owns the question *"what is mine, and what of it is still mine on
the next map"*. It sits between four ledgers that each own one piece and none of which owns the
join: [`claims/tavern.md`](tavern.md) owns the mercenary **pool**, [`claims/hero.md`](hero.md) the
hero's **stats**, [`claims/alm.md`](alm.md) the map's **type-5 group roster** (`ALM-GRP-041`), and
[`claims/sav.md`](sav.md) the save **container**. What the rows below add is the *carrier*: the
engine has no party object, and one thing that crosses a mission boundary is a serialized object
graph — **one** thing, not the only one (`PARTY-PERSIST-014`).

**Read `PARTY-ORIGIN-010` before any other row here.** "The party" is two containers on the
`Player` plus a pointer, and which one you implement decides which half of the game breaks: the
group list `+0x24` is what a save stores, the flat index `+0x20` is what the placement walk reads,
and `+0x20` is rebuilt from `+0x24` on load.

Two vocabularies meet here and must not be conflated. A **`Player`** (`0x70` bytes,
`CRuntimeClass` at `0x5c24f8`) is the simulation's owner object, one per map type-5 slot. A
**group** (`0x48` bytes) is a container of actors held *by* a `Player`. `ALM-GRP-041`'s "group" is
the map record a `Player` is built from, not this object.
